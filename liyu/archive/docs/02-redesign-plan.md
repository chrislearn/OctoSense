### 时间选择器

`OuyuSegmented`，三段：今天 / 明天 / 本周。选「本周」时下方展开一条 7 天日期条（日期 + 星期 + 强度圆点），可单选某一天。桌面态时间选择器与日期条同排。

### 「最可能遇见的地方」排序列表 —— 隐私约束是硬的

这是你提出的核心诉求，也是最容易踩隐私红线的地方。规则：

1. **只显示分档文案，绝不显示人数、百分比、更新时间。** 三档：`很可能` / `有可能` / `较少`，配 5 格强度条（图形只是分档的可视化，不是数值）。
2. **不满足匿名阈值的区域不参与排序。** `02-features.md` B 节要求「至少 5 位不同有效候选才显示熟人机会；阈值不满足时统一退为普通建议」。所以列表分两段：上半段是满足阈值的区域（按强度排序），下半段是「按公共活动强度给的普通建议」，后者不涉及任何熟人信息，且视觉上要能区分（不同的标签色 + 一句说明）。
3. **固定批次刷新（30 分钟），不随滚动、切区、切联系人实时变化。** 同一时间桶内结果稳定，避免用户通过反复切换做差分攻击。
4. **「下午最集中」这类时段提示只给到时段粒度（上午 / 下午 / 晚间），不给具体钟点。**

新增数据结构（`data.rs`）：

```rust
pub enum OppLevel { Likely, Possible, Few, BelowThreshold }

pub struct AreaOpportunity {
    pub area: usize,          // AREAS 下标
    pub day: usize,           // 距今天的天数 0..=6
    pub best_slot: Option<usize>,
    pub level: OppLevel,
}

/// 固定批次：同一 (day, batch_id) 返回同一结果。
pub fn opportunity_ranking(day: usize) -> Vec<AreaOpportunity>;
```

MVP 阶段这是本机生成的虚构数据（和现在的 `dev_toggle` 一样是演示），但**数据形状要按将来真接后端来定**，不要再写成散落的 Label 文案。

### 区域详情（点击列表行）

一个从底部升起的 sheet（`OuyuSheet`）：区域名 + 街区插图大图 + 这一天三个时段的分档 + 「我也去这儿」按钮（预填发布向导的第 2 步）。不放地址、不放坐标、不放公共地点的具体名字（避免变成「去这家店蹲人」）。

### 发布入口

- 手机：右下角常驻 FAB（`＋`），底部导航之上 16px，避开安全区。
- 桌面：顶部右侧主按钮「发布去向」。
- 已有有效发布时，FAB 图标换成铅笔，点进去是编辑当前发布。

## 三、发布流程独立成向导

从常驻长表单改成三步向导（手机全屏推入，桌面居中 dialog）：

| 步 | 内容 | 与规范的关系 |
|---|---|---|
| 1 · 什么时候 | 今天 / 明天 / 选某一天（本周内）+ 上午 / 下午 / 晚间 | 02 A 要求时段 ≥3 小时，三段划分不变；日期从「只有今天 / 明天」放宽到一周，与发现页的时间维度对齐 |
| 2 · 哪一带 | 区域选择器（见下） | 02 A：固定公共街区，1–2km 起步，不做住宅 / 医院等敏感标签 |
| 3 · 想做点什么 + 预览 | 三个通用意愿 + 「别人看到的就是这一行」预览 + 确认发布 | 沿用现有 `pub_preview`，这块做得是对的，保留 |

顶部一条三点进度指示；每步一个主按钮；返回不丢草稿，退出向导才丢（02 A：「退出编辑丢弃草稿」）。

### 区域选择器 —— 不接地图，但要做完整

现在只有 4 个写死的演示地址（`data.rs:17` 的 `AREAS`），这根本不能用。不接地图不等于地址将就，恰恰相反：**不接地图，就必须靠一份好的区域库把「填地址」这件事做简单**。

#### 区域库

新建 `apps/ouyu/src/areas.rs`，收录一个城市（北京）的**约 100 个公共片区**，按行政区分组、带类型与别名：

```rust
pub enum AreaKind { Commercial, Park, Waterfront, Culture, Office, Campus, Transit, Neighborhood }

pub struct Area {
    pub id: u16,
    pub name: &'static str,      // "三里屯一带"
    pub district: &'static str,  // "朝阳区"
    pub kind: AreaKind,
    pub alias: &'static str,     // "太古里 工体 酒吧街" —— 搜索命中用
    pub py: &'static str,        // "sltyd" —— 拼音首字母搜索
}
```

**收录标准（隐私约束，写进模块注释防止后人加错）**：

- 只收 **≥1km 的公共片区**：商圈、公园绿地、滨水步道、文化街区、办公园区、校园周边、交通枢纽、大型生活片区。
- **不收**：单个楼宇、门店、住宅小区、医院、诊所、学校内部、宗教场所、政府机构 —— 02 A 的「住宅、医院等敏感具体去向不做标签」。
- 名称一律用「…一带 / …周边 / …公共街区」的模糊措辞，不给精确地标。

- **搜索**：中文子串（名称 / 行政区 / 别名）+ 拼音首字母。输入「sltyd」或「太古里」或「三里屯」都能命中「三里屯一带」。
- **最近去过**：本机保存最近 5 个选过的区域（只是本机偏好，不进任何匹配输入）。
- **机会分档**：列表里直接带上所选那一天的分档，让「选哪儿」和「哪儿可能遇见」在同一屏里闭环。分档仍遵守阈值规则，不足阈值的不显示分档标记。

`Publish.area` 从 `usize` 下标改为 `u16` 的区域 id，`AREAS` 常量退役。后续扩城市时只需往 `areas.rs` 加数据。

### 为什么不接地图

**不接真实地图**，理由三条，两条产品、一条工程：

1. `05-visual-style.md` 写死了「**区域插图不是实时地图**」，`02-features.md` B 节写「地图仅为街区插图，无人形点、头像、距离、实时定位、缩放追踪」。接入可缩放真实底图后，用户的第一直觉一定是放大到街道、拖一个 pin 到具体位置 —— 这与「区域以 1–2km 起步」直接冲突，会把产品从「模糊去向」拉回「共享位置」。
2. 真实底图会把「我今天去哪」的心智从**选一个生活片区**变成**标一个点**。偶遇的整个隐私模型建立在前者上。
3. 工程上：Makepad 侧确实有能力 —— `widgets/src/map/view.rs:2637` 的 `MapView` 默认就是 `use_network: false` + `use_local_mbtiles: true`，纯离线矢量渲染，支持 `dark_theme`、`MapMarker` / `MapPuck` / `MapRouteOverlay`（`widgets/src/map/mod.rs:13`），不产生任何外部请求，与 05「无远程字体、图库、分析 SDK 或外部请求」兼容。**但仓库里没有任何 `.mbtiles` / `.mkmap` 资源** —— 要接就得先打一份城市级离线瓦片档进 `resources/`，体积和构建流程都要单独立项。

**二期可以接，前提是同时满足三条约束：**

1. 资源就位：一份城市级离线瓦片档，`use_network: false` 保持不变。
2. 锁缩放：`min_zoom` / `max_zoom` 都锁在区域级（约 z12–z13），用户**看得到自己在城市的哪一块，但看不到街道细节**。
3. 只读选择：地图上只渲染预设的粗区域多边形（点亮 / 未点亮两态），点击选中整块区域；不接受任意坐标、不能拖 pin、不显示自己的实时位置。

也就是说：地图是**区域选择器的皮肤**，不是地图。达不到这三条就继续用现在的 `OuyuMap` 街区插画 —— 它其实挺好，问题只是现在没被用在需要它的地方。

## 四、现场互认重设计（本轮最重要的一节）

### 设计原则

> 用户只做三件事：**选出对面是谁 → 允许定位 → 按一下确认**。
> 会话、短码、交叉校验、同地判定、重试次数 —— 全部是系统内部的事，一个字都不出现在正常路径上。

### 新流程（4 个用户可见状态）

```
① 选人             ② 定位门槛            ③ 等待确认           ④ 结果
┌───────────┐    ┌────────────┐     ┌───────────┐     ┌────────────┐
│刚刚见到谁？ │    │   [定位针]   │     │   ◠◡◠      │     │     ✓      │
│           │    │确认相遇需要  │     │已确认，等待 │     │与林舟的相遇 │
│(林) 林舟   │ →  │用一次定位    │  →  │林舟在现场也 │  →  │  已确认    │
│(陈) 陈晓   │    │只判断是否同地│     │确认        │     ├────────────┤
│(许) 许宁   │    │不上传坐标    │     │           │     │[券]+[店家] │
│           │    │完成即丢弃    │     │还可确认8:12│     │就在这一屏   │
│  ＋ 添加   │    ├────────────┤     ├───────────┤     ├────────────┤
├───────────┤    │[开启定位并确认]│    │  [取消]    │     │这次回忆…    │
│ [确认相遇] │    │[不开定位，只留 │    │⌄对方没有偶遇?│    │保存/隐藏/不存│
└───────────┘    │  一条回忆]   │     └───────────┘     └────────────┘
                 └────────────┘
```

### ① 选人

- 熟人用「首字圆形 + 姓名」的行，不用 chip。头像位是纯色圆底 + 姓氏首字（**不是真实头像** —— 规范全程禁止头像，这只是一个色块，用来给列表建立视觉节奏）。
- 底部一个主按钮「确认相遇」。**删掉入口处的「就记到这里 / 申请相遇礼」分叉**，也删掉入口处的「这次回忆怎么留」。
- 「本次不确认，只记一笔」作为一个不显眼的文字链留在页面底部 —— 有些人就是只想记录，但这不该是主路径。

### ② 定位门槛（新增状态 `RecogStage::LocationGate`）

这是你说的「必须打开定位功能后才能确认」的落点。一屏，三段文字讲清楚：

- **为什么**：判断你们当时是否真的在同一个地方
- **用多久**：只用这一次，最多 10 分钟
- **去哪了**：在你的设备上判断，只把「是 / 否」交给服务，不上传坐标，完成即丢弃

主按钮「开启定位并确认」；次出口「不开定位，只留一条回忆」。

> **已定稿**：定位是**领券路径的硬门槛** —— 不开定位就不建立互认会话、不进入确认。普通回忆路径不需要定位（本机一条记录，本来就不需要证明）。
>
> 券**不分「同地券 / 非同地券」**：走完确认就有券（除非限额 / 无库存），走不完就只有一条普通回忆。`design/02-features.md` D 节第 5 点和异常表已按此回写。

### ③ 等待确认（单一等待态）

一个状态屏，只有：进度环 + 「已确认，等待 {姓名} 在现场也确认」+ 真实倒计时「还可确认 8:12」+ 一个「取消」。

- **不显示会话码。** 短码 / 二维码收进一个折叠区「对方没有偶遇？」，展开后才出现二维码（免安装网页确认入口，`02-features.md` D 节第 3 点），短码作为二维码下方的小字 fallback。
- **不显示「我已确认对方是 X」按钮。** 在 ① 选人 + 点「确认相遇」的那一刻，本人提交就已经完成了，不需要第二次点。
- **不显示模拟区。** 模拟改为设置 → 开发者选项里的开关（见第七节）。产品态下这一屏自动推进。
- 倒计时用中性语气，不做恐吓式红色跳动（05：「不做连胜、排名、错过惩罚或倒计时恐吓」）。

### ④ 结果屏 —— 券和店家在同一屏直接出现

成功时，自上而下一屏内全部给到：

1. ✓ 与 林舟 的相遇已确认（一行小字：双方独立确认 + 同地校验通过，不披露对方资料）
2. **券面**（暖杏卡）：¥60 · 双人满 ¥120 可用 · 有效期至 x 月 x 日 · 商户赞助
3. **店家信息**：店名 + 地址 + 营业时间 + 距离档位（「步行可达」，**不给具体米数**）+ 「导航去这里」（跳系统地图，属于用户主动动作）
4. **另外最多 2 家可选店铺**，横向卡片（`02-features.md` E 节：最多 3 家）
5. 「这次回忆怎么留」：保存（默认）/ 隐藏 / 不保存 —— 从入口移到这里，符合 02 F「结束或离开成功页时按本次选择写入」
6. 「完成」

**取消「领取」这一步。** 确认成功 = 券已在手。原来的 `ck_claim` / `ck_redeem` 只保留「核销」（到店时出示），核销仍是一次显式动作。

### 异常统一成同一个结果屏，换文案和出口

| 情况 | 屏上文案 | 主出口 | 次出口 |
|---|---|---|---|
| 未开定位 | 不开定位就没法确认你们在同一个地方 | 开启定位 | 只留一条回忆 |
| 对方未确认 / 过期 | 这次没能双方确认 | 重新发起 | 只留一条回忆 |
| 信息不一致 | 双方信息尚未一致（不揭示谁填了谁） | 再试一次（还剩 2 次） | 只留一条回忆 |
| 同地不成立 | 相遇已确认，但当时你们不在同一个地方，这次没有相遇礼 | 记下这次相遇 | — |
| 券限额 / 无库存 | 相遇已确认。本周与林舟的相遇礼已经用过了 | 记下这次相遇 | — |
| 有人取消 | 这次确认已结束（不揭示谁取消） | 返回 | — |

「同地不成立」和「无库存」必须分开说清楚 —— `02-features.md` D 节异常表要求「**不能谎称验证失败**」。

## 六、视觉精致度 —— 把「不精致」拆成可执行项

### 1. 卡片分三级（现在只有一级）

| 内联行 | 列表项 | 无底色，底部 1px `#1b2942` 分隔线，padding 14 / 0 |

### 2. 排版比例（补上断层的 17 档，去掉 11px 正文）

### 3. 间距节奏

- 尺寸：lg 44（主操作）/ md 36（次操作）/ sm 28（行内）
- 状态：默认 / hover / pressed / **disabled** / **loading** —— 后两个现在完全没有
- 图标位：左侧图标 + 文字，或纯图标（正方形，用于 FAB 和工具按钮）
- 文案去掉「→」

### 5. 反馈体系

- 写入成功 → `OuyuToast`，2.5s 自动消失，从底部导航上方升起
- 异步动作 → 按钮 loading 态
- 删除类 → **5 秒 undo toast**（删回忆、撤回发布），而不是二次确认弹窗；只有「删除联系人及其全部回忆」这种不可逆操作保留二次确认

### 6. 空态组件 `OuyuEmpty`

统一「一个线性图形 + 一句话 + 一个动作按钮」。四处要用：熟人为空、回忆为空、成就 0 次（文案已定：「下一次偶然，值得期待」，06）、机会不足阈值。

### 7. 动效

只做 120ms 淡入 + 8px 位移；页面切换 160ms。必须尊重 `prefers-reduced-motion`（05）。**不做脉冲 / 呼吸效果暗示有人在移动**（05 明文禁止）。

### 8. 颜色 token 化

把现在散落在 `lib.rs` 的字面量 hex 收进一处：

```rust
// apps/ouyu/src/theme.rs
pub const BG:      u32 = 0x0b1220;

pub const PANEL_2: u32 = 0x152235;
pub const LINE:    u32 = 0x26364c;
```

## 七、真实应用还缺的东西

### 1. 首次启动引导（3 屏 + 隐私同意）

偶遇最大的风险是被当成「附近的人」来理解。第一次打开必须讲清楚三句话：

1. 这不是约人的 app —— 你不会看到谁在哪
2. 你只发布「今天下午 · 三里屯一带」这种模糊去向，别人看到的就是这一行
3. 定位只在你要确认一次真实相遇、领相遇礼的那一刻用一次，用完就丢

第 3 屏底部是隐私要点 + 「知道了，开始」。可跳过，但跳过后在「我」页保留入口。

### 2. 「我」页结构

```
我
├─ 成就（摘要 + 频率曲线 + 里程碑 + 数据表）   ← 06 全部内容
├─ 我的券   2 张可用                          ← 新增，见下
├─ 生成分享卡                                 ← 原 page_share
├─ 设置
│   ├─ 定位权限            已开启 / 去系统设置
│   ├─ 通知                发布到期提醒 / 券到期提醒
│   ├─ 数据与隐私          导出本机数据 / 清除本机数据 / 数据边界说明
│   └─ 开发者选项          草图场景切换（从发现页 devbar 移来）、模拟互认
└─ 关于偶遇                版本 / 设计原则 / 这个 app 不做什么
```

### 3. 「我的券」—— 补上功能漏洞

新增持久化的 `wallet: Vec<RewardClaim>`，`RewardClaim` 补字段：

```rust
pub struct RewardClaim {
    pub id: String,
    pub merchants: Vec<Merchant>,   // 最多 3 家（02 E）
    pub offer: String,
    pub threshold: String,
    pub expires_at: String,          // 最长 7 天（02 G）
    pub state: RewardState,          // Available | Redeemed | Expired
}
```

三个分区：可用 / 已核销 / 已过期。**券里不存联系人、不存坐标、不存相遇日期**（02 H 的 `RewardClaim` 模型明确「无联系人、坐标」）。这意味着券和回忆在本机也是两条不相交的记录 —— 这一点要在「我的券」页用一句话说明，否则用户会问「这张券是和谁的那次」。

### 4. 通知（只有两类，opt-in）

- 你的去向 30 分钟后到期
- 你有一张券还剩 2 天

**明确不做**：「附近有熟人」「有人和你去了同一个地方」—— 这类通知会直接把匿名机会变成实时位置广播，违反 02 B。这条要写进代码注释，防止以后有人「顺手加个功能」。

### 5. 四态统一组件

空 / 加载 / 错误 / 离线，四个都用同一个组件的不同 preset。现在一个都没有。

### 6. 回忆页

- 按月分组（`2026 年 9 月` 作为 sticky 分组头）
- 按人筛选（现有 `filt_row` 扩展）
- 单条详情：日期 + 称呼 + 备注编辑（`EncounterLocal.note` 字段已存在，缺入口）+ 隐藏 / 恢复 + 删除
- 搜索：**只搜称呼与备注，且隐藏记录不进搜索**（02 F：「隐藏记录不进入提醒、搜索、AI 或推荐」）

### 7. 熟人页

手动添加、字母索引、合并重复项。保持现有「只显示称呼 + 相遇次数 + 查看 / 删除」，不加任何在线 / 安装 / 亲密度状态（05 明文禁止）。

### 8. 成就页补齐

曲线下方加一个可展开的数据表（周 / 次数），06 明确要求且当前未实现。

### 9. 真实倒计时

会话 10 分钟要真的走，到点进 `Expired`。现在只是一行写死的文案。
