# 01 · 现状评审

站在「这是一个要给真人用的 app」的角度，把当前实现逐页看了一遍。结论先说：**规范（`design/`）写得比实现细，实现的问题不是没照着规范做，而是把规范里的「内部协议」当成了「用户界面」直接翻译出来。**

严重度：P0 = 业务/信任层面站不住；P1 = 能用但不像成品；P2 = 成品必备但可后置。

---

## P0 · 业务层面站不住

### 1. 互认流程把协议内部状态直接暴露成用户操作

`lib.rs:643-721` 的 `meet_session` 一屏里同时出现：

- `se_code`「会话码 1042 · 10 分钟有效」（`lib.rs:667`）
- `se_self`「我已确认对方是 林舟」（`lib.rs:679`）
- `se_sim_label`「—— 模拟区（代替真实对方与定位）——」（`lib.rs:691`）
- `se_sim` 三个按钮：模拟对方也确认 / 模拟信息不一致 / 模拟定位未授权（`lib.rs:701-709`）
- `se_loc` 两个按钮：重试定位 / 只留普通回忆（`lib.rs:711-717`）
- `se_cancel`「取消本次确认」（`lib.rs:719`）

`02-features.md` D 节的 `开始 → 会话建立 → 本人提交 → 等待双方 → 互认/同地校验 → 成功/不符合/过期/取消` 是**服务端状态机**，不是用户操作序列。现在 UI 和它一对一映射，导致用户被要求理解「会话」「短码」「本人提交」这些他不该知道的概念。

用户在一次真实相遇里应该只做三件事：**选出对面是谁 → 允许定位 → 按一下确认**。剩下的由系统对齐。

### 2. 定位是可跳过的旁支，不是前置条件

`data.rs:343` 的 `location_denied()` 只能从 `SelfDone` 进入，也就是**先确认、再问定位**。这既不符合业务（没有定位就无法判断同地，那份确认本来就是无效的），也让用户在已经付出确认动作之后才被要求授权，授权率必然低。

定位应该在确认动作**之前**作为一道明示的门槛：说清楚要用来干什么、用一次、不上传坐标，然后同意才能继续。

### 3. 成功之后券和店家信息没有「直接出现」

`meet_success`（`lib.rs:726+`）确实有 `coupon_card`，但它只给了券面（店名一行、金额、条款），缺少让券可用的信息：**地址、营业时间、距离档位、另外最多 2 家可选店铺**（`02-features.md` E 节写的是「推荐最多 3 家公共店铺」，实现只有 1 家）。

而且 `ck_claim` / `ck_redeem` 是两次点击才拿到券。成功页应当是「确认成功 = 券已在手 = 知道去哪家店」，领取这一步在业务上没有存在理由。

### 4. 相遇页入口逼用户先做一个他还不理解的选择

`pick_go`（`lib.rs:624-630`）并排放着「就记到这里」和「申请相遇礼 →」。用户刚见完朋友，打开 app，第一个要回答的问题变成了「你这次要不要券」。

正确顺序是：先确认相遇（统一路径），确认成功后**自然地**拿到券；不满足同地条件时再退化成普通回忆。「这次回忆怎么留」（`choice_row`，`lib.rs:606-612`）同理 —— 它现在在入口，而 `02-features.md` F 节明确写「结束或离开成功页时按本次选择写入」，本来就该在成功屏的末尾。

### 5. 已领的券没有任何地方可以再找到

`data.rs` 的 `reward: Option<RewardClaim>` 只有一张，且 UI 只在 `meet_success` 里渲染。**离开成功页，用户就再也找不到自己的券了**，也看不到有效期。这是一个实打实的功能漏洞，不是打磨问题。

## P1 · 能用，但不像成品

### 6. 发现页主次颠倒

当前自上而下是：hero → `devbar`（开发者条）→ `pub_card`（一张四段式长表单，`lib.rs:201-355`）→ `opp_card`（街区插图）→ echo → met。

用户打开「发现」想知道的第一件事是「**这几天、哪里最有可能遇见**」。现在第一屏是一张要他填四个 chip 组的表单，机会区被压到折叠线以下。

### 7. 没有时间维度，也没有排序结果

- 页面上没有任何「今天 / 明天 / 未来一周」的全局选择器。时间只作为发布表单里的一个字段（`pf_day_row`，`lib.rs:238-246`，且只有今天/明天两项）。
- 机会区 `opp_normal`（`lib.rs:381-406`）只有一张 `OuyuMap` 插图加两行说明文字，**没有任何按地点排序的结果**。信息密度接近零。

### 8. 发布应该是一个动作，不是一块常驻区域

`pub_card` 常驻首屏、占约 400px 高。发布是低频动作（每人只有一个有效发布，`02-features.md` A 节），应该收成一个明确的「发布」按钮，点进独立流程；发现页只保留一张紧凑的「我的当前发布」状态条。

### 9. 全应用零图标

`canvas.rs` 的 `OuyuNavTab` 是纯文字；底部五个 tab 没有图标，按钮也没有。整个 app 没有引用任何 SVG。而宿主壳自己有 42 个统一风格的线性图标（`resources/icons/`，通过 `DrawSvg` 绘制，见 `src/shell/ui.rs:637+`），偶遇一个都没用上，视觉上就和「系统里的一个正式应用」脱节了。

### 10. 视觉层级是平的

- 所有卡片同一个 `OuyuCard`、同一个 padding 18、同一个圆角、同一个底色，主卡和附注卡分不出轻重。
- 字号只有 22 / 13 / 12 / 11 四档，22 和 13 之间断层，缺 17 这一档做小标题。
- `05-visual-style.md` 明确写「**放弃旧版 11px 正文**」，但实现里 11px 被大量用于说明文字（`dev_note` `lib.rs:195`、`pub_badge` `lib.rs:226`、`opp_badge`、`se_sim_label`、`ck_badge` 等），不只用于徽章。
- 按钮统一用文字 +「→」表示前进（`pf_go`「预览别人看到的 →」、`btn_reward`「申请相遇礼 →」），这是网页草图的写法，不是 app 的写法。

### 11. 没有状态反馈体系

写入成功靠一个常驻 Label（`pick_done`，`lib.rs:632`）表示；没有 toast、没有按钮 loading 态、没有 undo。删除类操作（删回忆、删联系人、撤回发布）目前是直接生效。

### 12. 空态只是一行灰字

`pc_empty`（`lib.rs:588`）、稀疏场景 `opp_sparse`、成就 0 次 —— 都只有一句灰色文字。真实 app 的空态需要「一个图形 + 一句话 + 一个动作」。

### 13. 开发者条出现在产品首屏

`devbar`「草图场景 / 正常场景 · 切换稀疏」（`lib.rs:178-199`）在发现页顶部。应该移到设置里的开发者选项。

## P2 · 成品必备，可后置

| # | 缺口 | 依据 |
|---|---|---|
| 14 | 无首次启动引导与隐私说明 | 偶遇的核心卖点是「它不是约人的 app」，这件事必须在第一次打开时讲清楚，否则用户会按「附近的人」去理解它 |
| 15 | 无设置页 / 隐私页 | 定位权限状态、通知开关、本机数据导出与清除、`02-features.md` G 节的数据边界表，目前无处安放 |
| 16 | 无通知 | 至少需要「发布即将到期」「券即将过期」两类；**不能**做「附近有熟人」类通知（违反 B 节匿名约束） |
| 17 | 回忆页无分组/搜索/详情 | 当前是一条平铺列表 + 一个筛选行（`filt_row` / `mem0..mem7`）。备注字段 `EncounterLocal.note` 存在但没有编辑入口 |
| 18 | 成就曲线没有数据表 | `06-achievements-sharing.md` 明确要求「可展开数据表，不依赖 hover 才读到数字」，未实现 |
| 19 | 会话 10 分钟只是文案 | `se_code` 写死「10 分钟有效」，没有真实倒计时 |
| 20 | 桌面右列价值低 | `aside`（width 300）目前只是静态解释文字，没有随页面变化的上下文价值 |
| 21 | 颜色全是字面量 hex | `lib.rs` 里 `#e7edf8` / `#a4b2c9` 等散落数百处，没有 token 层，将来换肤或与宿主主题联动会很痛 |
| 22 | 无障碍未落地 | `05-visual-style.md` 要求焦点可见、字段有 label、状态 live region；Makepad 端可行性需单独评估 |
| 23 | `lib.rs` 4572 行单文件 | 五个页面的 widget 树全在一个 `script_mod!` 里，已经到了改一处要翻很久的程度 |
